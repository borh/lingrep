# lingrep 0.8.2

This release fixes writing corpora on Windows drives through WSL and on USB
drives, handles text files saved by Japanese Windows and macOS tools, and adds
commands to find and delete prepared corpora that a rebuild has replaced.
Install it as before:

```bash
curl --proto '=https' --proto-redir '=https' --tlsv1.2 -fsSLO https://github.com/borh/lingrep/releases/latest/download/install.sh
sh install.sh
```

## Fixes

### Windows drives through WSL, and USB drives

- `ling corpus build --output /mnt/c/...` failed in 0.8.1 with
  "Permission denied (os error 13)", although the 0.8.1 release notes said
  that corpora could be written there. Building a corpus, writing a count
  table, `ling serve` and `ling matches --ending-report` now work on `/mnt/c`.
- On macOS 15, `ling corpus build` to a FAT32 drive failed with
  `invalid provenance.sqlite format`. It now succeeds.
- `ling matches --ending-report` on an exFAT or FAT drive on macOS lost the
  report after the whole scan. The report is now written.
- When writing a corpus fails, the error names the file and what `ling` was
  doing, such as "cannot rename '…' to '…'", instead of only
  "Permission denied".

These cases now run in CI on FAT, exFAT, NTFS, case-insensitive ext4 and
APFS drives, and on `C:` from WSL 2.

### Text from Japanese Windows and macOS

- A byte-order mark at the start of a file, which Notepad and Excel write
  when saving UTF-8, is no longer read as text. In 0.8.1 it became part of
  the first word of a plain-text, Markdown or Soranoha document, and a JSONL
  or CoNLL-U file that started with one could not be read.
- A file in Shift_JIS fails with the file name, line and byte position, and
  the message gives a command that converts it to UTF-8:

  ```bash
  iconv -f CP932 -t UTF-8 old.txt > new.txt
  ```

  The same applies to `.lx` catalogs. A `.zip` file given as plain text fails
  with a message to unzip it, or to read a Soranoha archive with
  `--input-format soranoha`.
- When a pattern has a syntax error at a full-width character typed with
  the Japanese IME, such as `［`, `＝` or a full-width space, the error says
  which ASCII character to type instead. lingrep-web's editor and question
  page show the same note in Japanese.
- A value written in Japanese or typographic quotes, such as `[text=「猫」]`
  or `[text=”猫”]`, is an error. In 0.8.1 the catalog compiled and the
  pattern found nothing.
- Text copied from a PDF can spell `ガ` as `カ` followed by a separate voiced
  mark. A pattern value spelled that way now matches the corpus, with the
  warning `literal_normalized`. In 0.8.1 it found nothing.
- File names created on a Mac spell `ガ` the same way. A corpus folder copied
  from a Mac now gets the same document names, and for plain text, Markdown
  and JSONL the same identity, as the same files created on Windows or
  Linux. If two files in one corpus have names that differ only in this
  spelling, `ling` stops and names both.

## New: finding and deleting replaced corpora

Each time a dictionary, analyzer or `ling`'s reader changes, `ling corpus
build` writes a new prepared corpus beside the old one, and the old one
stays on disk. Two commands manage them:

```bash
ling corpus disk corpora/                      # size and status of each corpus and count table
ling corpus prune corpora/                     # lists what would be deleted
ling corpus prune corpora/ --execute           # deletes it
```

By default `prune` deletes only corpora of the current source files that
were built with another dictionary, analyzer or token format, and the count
tables that belong only to them, because rebuilding reproduces them. It
keeps the rest and gives the reason for each. If you built the corpus with
`-d`, `--input-format` or `--analyzer-config`, give `prune` the same options,
so that it treats that build as the current one. It never deletes a folder
that holds a file `ling` did not write, and it deletes nothing for a source
that has no current corpus unless `--keep` names one. See
[Pruning superseded artifacts](../cli-usage-guide.md#pruning-superseded-artifacts)
in the CLI guide.

## Upgrading

Corpora and count tables prepared with 0.8.1 work with 0.8.2 without
rebuilding, including their reading sidecars in `ling serve`.

`ling` 0.8.2 reads plain-text, Markdown and Soranoha sources with a new
reader revision, because it drops the byte-order mark. Running `ling corpus
build` again on such a source therefore writes a new corpus beside the
0.8.1 one instead of reusing it. Once it is built, the 0.8.1 corpus is
listed by `ling corpus prune` as kept, with the reason `reader_variant`;
`--include-all-superseded` deletes it.

`ling corpus render` still writes a reading sidecar for a Markdown corpus
built by 0.8.1, except in two cases, in which you rebuild the corpus first:

- a source file starts with a byte-order mark: the error says that
  re-reading the file "does not reproduce the stored sentences";
- a file or folder name is in the Mac spelling described above: the error
  says the source tree has another source identity than the corpus records.

A catalog whose text is all NFC, which is every catalog typed on Windows or
Linux, keeps its fingerprint, so saved question links stay valid.

Adapter wheels use version 0.8.2. See the
[changelog](../../CHANGELOG.md) for the complete list of changes.
